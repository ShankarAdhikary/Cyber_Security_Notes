# Level 3: Kernel and System Calls

## Goal
Understand what the kernel does, how programs request its services, and how to inspect kernel state.

---

## 3.1 Kernel responsibilities

**Concepts**
The kernel handles five main jobs:
- **Process management:** creating, scheduling, and stopping processes
- **Memory management:** giving each process its own virtual address space
- **Filesystems:** organizing and protecting stored data
- **Networking:** the TCP/IP stack and packet handling
- **Device drivers:** talking to hardware

**Key commands**
```bash
uname -r                 # running kernel version
cat /proc/version        # kernel build details
```

---

## 3.2 System calls

**Concepts**
- A **system call (syscall)** is how a user-space program asks the kernel to do something privileged (open a file, create a process, send a packet).
- Programs usually reach syscalls through libc wrappers (for example, `open()`, `read()`, `fork()`).
- Each syscall is checked by the kernel for permissions before it runs.

**Key commands**
```bash
strace ls                       # show syscalls made by a command
strace -e openat cat /etc/hostname   # filter to one syscall
sudo strace -p <PID>            # attach to a running process (lab use)
```

**Security relevance:** Tools like `strace` reveal what a program really does. Malware analysts use it to see file access and network calls. Attackers look for syscall abuse and kernel exploits.

**Practice**
- Run `strace -c ls` and identify the three most frequent syscalls.

---

## 3.3 Kernel space and the boundary

**Concepts**
- Revisit Level 1: user code crosses the system call boundary to reach kernel code.
- Kernel code runs in a privileged CPU mode (ring 0 on x86). User programs run in ring 3.
- A kernel crash appears as a **kernel panic**.

**Key commands**
```bash
sudo dmesg | tail -n 30      # recent kernel messages
sudo dmesg -T | grep -i error
```

---

## 3.4 Kernel modules

**Concepts**
- Modules are pieces of kernel code (drivers, filesystems) that load and unload at runtime without rebooting.
- They live under `/lib/modules/$(uname -r)/`.
- Loaded modules are listed in `/proc/modules` or `lsmod`.

**Key commands**
```bash
lsmod                        # loaded modules
modinfo <module>             # details about a module
sudo modprobe <module>       # load a module (with dependencies)
sudo modprobe -r <module>    # unload it
```

**Security relevance:** Rootkits often load a malicious kernel module to hide processes and files. Check for unexpected modules with `lsmod` and compare against known-good baselines. Blacklisting unused modules (in `/etc/modprobe.d/`) reduces attack surface.

**Practice**
- Run `lsmod | head` and pick one module. Use `modinfo` to read its description.
- Create a file in `/etc/modprobe.d/` that blacklists a module you do not need, then test it in your VM.

## 3.5 /proc: the process and kernel information interface

**Concepts**
- `/proc` is a virtual filesystem. Its files are generated by the kernel in real time.
- Each running process has a folder named by its PID (for example, `/proc/1234/`).

**Key files**
| Path | Contents |
|---|---|
| `/proc/cpuinfo` | CPU details |
| `/proc/meminfo` | memory usage |
| `/proc/mounts` | mounted filesystems |
| `/proc/<PID>/cmdline` | command that started the process |
| `/proc/<PID>/exe` | the binary being run |
| `/proc/<PID>/fd/` | open file descriptors |
| `/proc/<PID>/environ` | environment variables (readable by owner or root) |
| `/proc/net/tcp` | active TCP connections |

**Key commands**
```bash
cat /proc/cpuinfo | grep "model name" | head -1
ls -l /proc/self/exe         # the current process's binary
sudo ls -l /proc/$$/fd       # file descriptors of your shell
```

**Security relevance:** `/proc` is the main enumeration source during post-exploitation. Attackers read `/proc/<PID>/environ` for secrets and `/proc/net/tcp` for connections.

---

## 3.6 /sys: the device and kernel object interface

**Concepts**
- `/sys` (sysfs) exposes devices, drivers, and kernel settings as a tree of files.
- Some files are read-only information; others let you change settings.

**Key commands**
```bash
ls /sys/class/net            # network interfaces
cat /sys/class/net/*/address # MAC addresses
ls /sys/block                # block devices
```

---

## 3.7 Kernel tuning with sysctl

**Concepts**
- `sysctl` reads and changes kernel parameters, stored under `/proc/sys/`.
- Settings persist through `/etc/sysctl.conf` or files in `/etc/sysctl.d/`.

**Key commands**
```bash
sysctl -a | head              # list parameters
sysctl net.ipv4.ip_forward    # check IP forwarding
sudo sysctl -w net.ipv4.ip_forward=0   # change temporarily
```

**Security relevance:** Hardening often means setting parameters such as disabling IP forwarding on hosts that should not route, enabling `kernel.randomize_va_space`, or restricting `kernel.dmesg_restrict`.

**Practice**
- Check `kernel.randomize_va_space`. A value of `2` means full ASLR is enabled.
- Find which parameters are set in `/etc/sysctl.d/`.
